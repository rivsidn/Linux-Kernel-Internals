# Linux-2.6.12

## 基本概念

> Generic mechanism for defining kernel helper threads for running arbitrary tasks in process context.

一种通用机制，用于:

1. 定义内核线程
2. 进程上下文中执行任意任务


## 数据结构

### workqueue_struct

工作队列结构体，对应一个工作队列.

分两种:

- 单线程
  只会创建一个线程，不绑定CPU.
- 多线程
  会创建多个线程，每个CPU绑定一个线程.

### cpu_workqueue_struct

对应一个具体的工作单元，多线程时，每CPU一个，包含这几部分内容:

1. 执行的线程
2. 没工作时线程的等待队列
3. `work_struct` 链表表头
4. 其他用于管理的成员(锁等)

### work_struct

对应一个具体的可执行任务.

## API接口

| API                           | 说明                           |
|-------------------------------|--------------------------------|
| create_workqueue              | 创建多线程工作队列             |
| create_singlethread_workqueue | 创建单线程工作队列             |
| flush_workqueue               | 工作队列刷新                   |
| destroy_workqueue             | 工作队列销毁                   |
| queue_work                    | 添加工作任务到工作队列         |
| queue_delayed_work            | 添加一个延迟工作任务到工作队列 |


## 核心算法

### 工作队列刷新

为了防止刷新工作队列的时候，一直有进程向工作队列中添加任务，导致刷新函数无法退出。

这里设置了序列号.

**flush_cpu_workqueue() 刷新函数**

```c
		sequence_needed = cwq->insert_sequence;

		while (sequence_needed - cwq->remove_sequence > 0) {
			//...
			schedule();
			//...
		}
```

**run_workqueue() 工作队列执行函数**

```c
		cwq->remove_sequence++;
```

仅等待执行刷新操作之前的插入任务结束之后便可以结束刷新操作.

## 常见疑问

- destroy_workqueue 函数执行后，添加到工作队列的任务一定会被执行么？

  不保证会被执行.

  需要分几种情况讨论这个问题:

  - 单线程工作队列

    主要涉及三个动作:
    1. queue_work 任务添加
    2. destroy_workqueue 工作队列取消
    3. worker_thread 工作队列执行

    这三个任务可能分别在三个不同的CPU上执行，执行顺序如下:

    1. CPU0 执行清空worklist 之后返回
    2. CPU1 添加任务到工作队列中
    3. CPU2 销毁工作队列
    4. CPU0 检查线程是否可以结束，直接结束，CPU1 插入的任务不会被执行.

  - 多线程工作队列

    多线程工作队列，由于`schedule_delayed_work_on()` 函数的存在，所以这里的流程
    是类似的.
    也是无法保证一定会被执行.

- `more_work` 等待队列会加入几个进程？

  此处的工作队列只会加入一个进程.

- 什么时候适合选择工作队列？

  >  选择workqueue的原则：
  >
  >  使用workqueue当：
  >  - 需要睡眠/阻塞
  >  - 处理时间较长（毫秒级）
  >  - 需要使用进程上下文
  >  - 对实时性要求不高
  >
  >  不适用workqueue当：
  >  - 需要极低延迟（使用tasklet/softirq）
  >  - 处理非常简单快速（直接在中断处理）
  >  - 对时序要求严格（使用专门的实时机制）
