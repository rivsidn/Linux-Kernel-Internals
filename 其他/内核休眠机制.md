#### 介绍一下当前系统的休眠机制

• 当前这份 Linux 4.19.190 源码里的休眠机制是典型的 swsusp / suspend-to-disk：把当前内存状态做成休眠镜像，写入 swap，然后关机、重启或进入平台 S4；下次启动时新启动的内核从 swap 找到镜像，
  把内存恢复到旧内核状态，再跳回当时保存的位置继续执行。

  当前配置

  - .config:411 启用了 CONFIG_HIBERNATION=y，所以内核支持休眠。
  - .config:408 启用了 CONFIG_SUSPEND=y，因此也支持普通 suspend，并且 /sys/power/disk 里可能有 suspend 模式。
  - .config:412 的 CONFIG_PM_STD_PARTITION="" 为空，所以默认没有编译期 resume 分区，通常需要通过启动参数 resume= 或 /sys/power/resume 指定恢复设备。
  - .config:407 启用了 CONFIG_ARCH_HIBERNATION_HEADER=y，休眠镜像里会包含架构相关校验信息。

  入口

  - 用户态常见触发方式是写 disk 到 /sys/power/state。
  - kernel/power/main.c:496 先识别字符串 disk。
  - kernel/power/main.c:533 在识别到 disk 后调用 hibernate()。
  - 休眠模式由 /sys/power/disk 控制，支持 platform、shutdown、reboot、suspend、test_resume 等，定义在 kernel/power/hibernate.c:920。
  - resume 设备可以通过 /sys/power/resume 设置，入口在 kernel/power/hibernate.c:1049；启动参数包括 resume=、resume_offset=、noresume、nohibernate、hibernate=nocompress 等，在 kernel/
    power/hibernate.c:1167 之后处理。

  保存流程
  大致调用链如下：

  echo disk > /sys/power/state
    -> hibernate()
    -> hibernation_snapshot()
    -> create_image()
    -> swsusp_arch_suspend()
    -> swsusp_save()
    -> swsusp_write()
    -> power_down()

  关键步骤：

  - hibernate() 是主流程，负责加 system_transition_mutex、调用 PM notifier、同步文件系统、冻结用户进程、创建设备/内存位图，见 kernel/power/hibernate.c:696。
  - 进入休眠前先 ksys_sync() 同步文件系统，避免镜像创建失败后数据丢失，见 kernel/power/hibernate.c:721。
  - freeze_processes() 冻结用户进程，避免用户态继续修改内存和文件系统状态，见 kernel/power/hibernate.c:725。
  - hibernation_snapshot() 会预分配镜像内存、冻结内核线程、冻结设备，见 kernel/power/hibernate.c:352。
  - hibernate_preallocate_memory() 会按 /sys/power/image_size 和 /sys/power/reserved_size 目标预留足够内存，避免保存镜像过程中再大量分配失败，见 kernel/power/snapshot.c:1671。
  - create_image() 进入最关键的原子阶段：冻结设备 late/noirq 回调、停非 boot CPU、关中断、挂起 syscore，然后调用架构相关的 swsusp_arch_suspend()，见 kernel/power/hibernate.c:275。
  - x86_64 上 swsusp_arch_suspend 保存寄存器后调用 swsusp_save()，见 arch/x86/power/hibernate_asm_64.S:26 和 arch/x86/power/hibernate_asm_64.S:51。
  - swsusp_save() 统计可保存页、分配副本页、复制内存页，最终形成内存中的休眠镜像，见 kernel/power/snapshot.c:1967。

  这里有个重要变量：in_suspend 定义为 __nosavedata，见 kernel/power/hibernate.c:48。它用来区分“刚创建完镜像准备写盘”还是“已经从镜像恢复回来”。

  镜像格式与写盘

  - 镜像由 snapshot_read_next() 以连续页流的方式输出：第一页是 struct swsusp_info 头，后面是元数据页，再后面是数据页副本，见 kernel/power/snapshot.c:2039 和 kernel/power/
    snapshot.c:2087。
  - struct swsusp_info 记录内核版本、系统名、物理页数量、镜像页数等，用于恢复时校验，见 kernel/power/power.h:8。
  - swsusp_write() 负责把镜像写入 swap，默认走 LZO 压缩路径；如果启动参数 hibernate=nocompress，则写未压缩镜像，见 kernel/power/swap.c:903 和 kernel/power/swap.c:935。
  - swap 的头部会被写成休眠签名 HIBERNATE_SIG，同时保存原始 swap 签名、镜像首扇区、flags、CRC32 等，见 kernel/power/swap.c:107 和 kernel/power/swap.c:307。
  - 镜像写完后 power_down() 按 /sys/power/disk 当前模式关机、重启、进入平台 S4，或进入 suspend-to-RAM，见 kernel/power/hibernate.c:623。

  恢复流程
  下次开机时，恢复不是由 bootloader 直接完成，而是新启动的内核完成：

  boot kernel
    -> software_resume()
    -> swsusp_check()
    -> swsusp_read()
    -> hibernation_restore()
    -> resume_target_kernel()
    -> swsusp_arch_resume()
    -> 跳回旧内核 swsusp_arch_suspend() 返回点

  关键步骤：

  - software_resume() 是 late_initcall_sync，等设备枚举完成后查找休眠镜像，见 kernel/power/hibernate.c:805 和 kernel/power/hibernate.c:917。
  - 它通过启动参数或 sysfs 设置的 resume 设备定位 swap，然后调用 swsusp_check() 检查休眠签名，见 kernel/power/hibernate.c:843 和 kernel/power/swap.c:1512。
  - swsusp_check() 找到镜像后会把 swap 原始签名恢复回去，避免恢复失败后 swap 永久不可用，见 kernel/power/swap.c:1527。
  - swsusp_read() 读取镜像头、元数据和数据页；压缩镜像走 load_image_lzo()，未压缩镜像走 load_image()，见 kernel/power/swap.c:1477。
  - snapshot_write_next() 根据镜像中的 PFN 元数据安排页面写入位置，必要时先写入“安全页”，形成 restore_pblist，避免恢复过程覆盖当前执行中的恢复内核内存，见 kernel/power/snapshot.c:2568。
  - hibernation_restore() 冻结设备并进入原子恢复阶段，见 kernel/power/hibernate.c:516。
  - resume_target_kernel() 停非 boot CPU、关中断、挂起 syscore、恢复 highmem，然后调用 swsusp_arch_resume()，见 kernel/power/hibernate.c:441。
  - x86_64 的 swsusp_arch_resume() 设置临时页表、搬移恢复代码，然后调用 restore_image() 把保存的页面复制回原地址，见 arch/x86/power/hibernate_64.c:188 和 arch/x86/power/
    hibernate_64.c:201。
  - 页面恢复完成后，CPU 跳回保存镜像时的上下文；从代码视角看，控制流“神奇地”回到 swsusp_arch_suspend() 返回处，注释在 kernel/power/hibernate.c:310。

  平台休眠

  - 如果平台提供 platform_hibernation_ops，例如 ACPI S4，内核会默认使用 platform 模式。
  - hibernation_set_ops() 注册平台回调，见 kernel/power/hibernate.c:80。
  - ACPI 的 S4 回调在 drivers/acpi/sleep.c:1184 定义，并在支持 S4 时注册，见 drivers/acpi/sleep.c:1247。
  - 平台模式下，保存镜像后会调用平台的 enter() 进入真正的固件休眠状态，见 kernel/power/hibernate.c:543。

  用户态接口
  除了内核直接写 swap 的路径，还有 /dev/snapshot 给用户态休眠工具使用：

  - /dev/snapshot 是 misc 设备，minor 为 231，见 kernel/power/user.c:33 和 kernel/power/user.c:474。
  - 它提供 SNAPSHOT_FREEZE、SNAPSHOT_CREATE_IMAGE、SNAPSHOT_ATOMIC_RESTORE、SNAPSHOT_SET_SWAP_AREA 等 ioctl，见 include/uapi/linux/suspend_ioctls.h:16。
  - 这条路径允许用户态负责镜像压缩、加密、写入位置管理等，内核仍负责冻结、创建镜像和原子恢复。

####  内核中的cstate 跟这里的休眠什么关系

• 关系可以一句话概括：C-state 是“CPU 空闲省电状态”，休眠 hibernation 是“整机系统睡眠状态/S4 或关机 + 内存镜像恢复”，两者不是同一个层级。

  区别

  - C-state：CPU 级别状态，通常只在系统还处于工作态 S0 时使用。比如 C0 表示 CPU 正在执行，C1/C2/C3/... 表示越来越深的 idle 状态，功耗更低、唤醒延迟更大。内核里主要由 cpuidle 管，文档见
    Documentation/cpuidle/core.txt:8。
  - 休眠 hibernation：系统级状态，也叫 suspend-to-disk。内核把内存快照写入持久存储，然后关机、重启或进入平台 S4。文档描述在 Documentation/admin-guide/pm/sleep-states.rst:105。

  和当前休眠流程的关系

  - 休眠不是“让 CPU 进某个深 C-state”。当前路径是 hibernate() 创建内存镜像，然后 swsusp_write() 写到 swap，最后 power_down() 关机/重启/进平台 S4。
  - 在创建镜像前，内核会把非 boot CPU 下线：disable_nonboot_cpus() 出现在 kernel/power/hibernate.c:289 和 kernel/power/hibernate.c:576。这个过程中 CPU 可能会经过 idle/C-state，但这只是
    准备步骤，不是休眠的目标状态。
  - 休眠完成后如果是 shutdown 模式，机器基本断电；如果是 platform 模式，走 ACPI S4 等平台休眠，入口在 kernel/power/hibernate.c:543，ACPI 注册在 drivers/acpi/sleep.c:1184。
  - 恢复时不是从 C-state 唤醒回来，而是重新启动一个 restore kernel，再从 swap 读镜像，覆盖当前内存并跳回 image kernel。

  容易混淆的一点

  - suspend-to-idle 和 C-state 关系更近：它会冻结用户态、挂起设备，然后让 CPU 尽量待在 deepest idle states，文档见 Documentation/admin-guide/pm/sleep-states.rst:24 到 Documentation/
    admin-guide/pm/sleep-states.rst:32。
  - 但 suspend-to-idle 不是 hibernation。它不写内存镜像，内存仍然保留；而 hibernation 会写镜像并可以断内存电。

  调参影响

  - intel_idle.max_cstate=、processor.max_cstate=、cpuidle.off=1 这类参数主要影响 CPU idle、s2idle 功耗/延迟。
  - 对当前 echo disk > /sys/power/state 这种 hibernation 路径，它们一般不决定最终能不能休眠；真正关键的是 swap/resume 配置、设备 suspend/resume 回调、ACPI S4 支持、镜像大小和恢复校验。
  - 不过某些平台 bug 可能表现为“深 C-state 影响 suspend/resume 稳定性”，但那通常是平台/固件问题，不是 hibernation 机制本身依赖 C-state。


› s2idle 是 hibernation 的一种方式，可以这么理解不


• 不建议这么理解。更准确地说：

  s2idle 不是 hibernation 的一种方式，而是 suspend 的一种方式。

  可以这样分层：

  系统睡眠状态
  ├── suspend
  │   ├── s2idle / freeze       不写磁盘，靠 CPU idle + 设备挂起
  │   ├── standby / shallow     平台浅睡
  │   └── suspend-to-RAM / deep 通常对应 ACPI S3
  └── hibernation / disk        写内存镜像到磁盘/swap，然后断电或进 S4

  核心区别

  - s2idle：内存内容还在 RAM 里，CPU/设备进入低功耗，靠唤醒中断直接恢复。掉电会丢状态。
  - hibernation：内存内容先保存成镜像写到 swap/磁盘，然后可以完全断电。下次开机由新内核读镜像恢复。
  - s2idle 恢复路径：从 idle/wakeup interrupt 回来，继续原内核运行。
  - hibernation 恢复路径：重新启动 kernel，software_resume() 读镜像，再覆盖内存跳回旧内核。

  在这份代码里的入口也不同

  - s2idle：
      - echo freeze > /sys/power/state
      - 或 echo s2idle > /sys/power/mem_sleep; echo mem > /sys/power/state
      - 走 pm_suspend(PM_SUSPEND_TO_IDLE)，核心在 kernel/power/suspend.c。
  - hibernation：
      - echo disk > /sys/power/state
      - 走 hibernate()，核心在 kernel/power/hibernate.c。

  容易混淆的地方
  /sys/power/disk 里可能有一个 suspend 模式，这个看起来容易让人误解。

  它的含义不是“s2idle 是 hibernation”，而是类似 hybrid sleep：

  先创建 hibernation 镜像并写盘
  然后不马上关机，而是进入 suspend

  这样如果 suspend 期间没掉电，就快速从 suspend 恢复；如果掉电了，还能靠磁盘里的 hibernation 镜像恢复。

  在当前代码里对应 kernel/power/hibernate.c:628：

  if (hibernation_mode == HIBERNATION_SUSPEND) {
      error = suspend_devices_and_enter(PM_SUSPEND_MEM);

  也就是说这是 hibernation + suspend 的组合模式，不是 s2idle 本身变成了 hibernation。

  一句话总结：s2idle 是“不写盘的轻量系统挂起”；hibernation 是“写盘后断电/进 S4”；二者可以在 hybrid sleep 里组合，但不是包含关系。

  写盘不是更进一步么？为什么不是包含关系


• “写盘更进一步”这个直觉没错，但它不是在 s2idle 这条路径上“加一步”，而是换了一套恢复模型。

  更准确地说：

  s2idle = 保持 RAM 内容不丢，然后让系统低功耗等待中断唤醒
  hibernation = 把 RAM 内容复制到磁盘，然后允许 RAM 断电，之后靠重新启动恢复

  所以区别不是“有没有多写一步盘”，而是系统状态保存在哪里、怎么恢复完全不同。

  为什么不是包含关系

  - s2idle 的前提是 RAM 还活着：CPU/设备睡下去，但内存内容仍在，唤醒后直接继续跑原来的内核。
  - hibernation 的前提是 RAM 可以死掉：状态已经写到磁盘，恢复时先启动一个新内核，再读镜像覆盖内存，跳回旧内核。
  - s2idle 的恢复入口是中断唤醒后的 suspend resume 路径。
  - hibernation 的恢复入口是 boot 之后的 software_resume()。
  - s2idle 不需要创建内存镜像；hibernation 不需要最后一定进入 s2idle，它可以直接关机、重启或进 ACPI S4。

  可以类比成：

  s2idle      = 电脑合盖睡眠，内存还供电
  hibernation = 保存现场到硬盘，然后关机

  “保存到硬盘”确实更持久，但它不是“更深的 s2idle”，而是另一种保存现场的方式。

  hybrid sleep 为什么容易让人觉得包含
  hybrid sleep 做的是：

  先 hibernation 写镜像
  再进入某种 suspend

  目的有两个：

  - 如果没掉电：从 suspend 快速恢复。
  - 如果掉电了：从 hibernation 镜像恢复。

  但这叫“组合”，不是“包含”。因为第二步 suspend 失败或不用，也不影响 hibernation 本身成立；反过来，普通 s2idle 也完全不写镜像。

  另外在你这份 4.19 代码里，/sys/power/disk 的 suspend 模式调用的是：

  suspend_devices_and_enter(PM_SUSPEND_MEM);

  位置在 kernel/power/hibernate.c:628。也就是说它更接近“写完 hibernation 镜像后进入 suspend-to-RAM”，不是把 s2idle 当成 hibernation 的子状态。

  一句话再压缩一下：hibernation 比 s2idle“更持久”，但不是 s2idle 的加强版；它们一个靠 RAM 保现场，一个靠磁盘保现场，恢复路径不同，所以不是包含关系。
