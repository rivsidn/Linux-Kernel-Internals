# Linux-2.6.12

## 等待队列

### 唤醒

```c
condition = 1;
spin_lock_irqsave();
list_for_each_safe() {
	<write_barrier>;
	current->state = TASK_RUNNING;
}
spin_unlock_irqrestore();

```

### 休眠
```c
for (;;) {
	spin_lock_irqsave();
	add_wait_queue();
	current->state = TASK_INTERRUPTIBLE;
	<general barrier>;
	spin_unlock_irqrestore();
	if (condition)
		break;
	schedule();
}
```

由于自旋锁的存在，可以将唤醒、休眠分成几个事件: W1 W2 S1 S2 .

W1: 释放资源
W2: 唤醒进程
S1: 进程休眠
S2: 检查资源

屏障存在时，W1 W2，S1 S2  的相对顺序是固定的，排列组合可以发现不会出问题，都可以
正常唤醒.

没有内存屏障的情况下，W1 S2 移动到锁内，但是由于锁的半透屏障作用，不会穿过锁，此
时，事件可以简化成W S 两个，相互之间互斥.

这种情况下，还是不会存在唤醒丢失问题，所以此处内存屏障的使用可以理解为`store
buffer`、`invalidate queue` 刷新机制，藉由这种方式快速同步CPU 间内存状态.

1. 唤醒时
   休眠时只关注condition 状态，所以这里只需要"write barrier" 即可.

2. 休眠时
   此处的内存屏障是在 set_current_state() 中封装的，所以需要考虑到该函数的使用场
   景，写屏障用于通知该进程状态、读屏障执行之后可以快速获取condition 状态，所以
   此处使用了"general barrier".

综上，可以理解此处内存屏障的使用.









## 定时器操作

### 定时器删除
```c
int del_timer(struct timer_list *timer)
{
	//...
	list_del(&timer->entry);
	smp_wmb();
	timer->base = NULL;
	//...

	return 1;
}
```

### 定时器修改

```c
int __mod_timer(struct timer_list *timer, unsigned long expires)
{
	// 为空
	old_base = timer->base;

	spin_lock(&new_base->lock);

	internal_add_timer(new_base, timer);

	spin_unlock(&new_base->lock);

	return ret;
}
```

### 解释说明

按照 '55c888d6d09a [PATCH] timers fixes/improvements' 中的说法:

> We also don't need barriers. del_timer() and __run_timers() used smp_wmb()
> before clearing timer's pending flag. It was needed because __mod_timer()
> did not lock old_base if the timer is not pending, so __mod_timer()->list_add()
> could race with del_timer()->list_del(). With this patch these functions are
> serialized through base->lock.

此处的内存屏障是为了，当 timer->base 为空时，`__mod_timer()` 无法获取到old_base->lock，
所以此处链表操作可能会出现race.

但是，实际上这里`__mod_timer()` 代码无法保证在 `internal_add_timer()`中能够感知
到`del_timer()` 中的链表操作.

`spin_lock()` 无法代替`smp_rmb()`.

所以说，这里的代码应该是有问题的.
